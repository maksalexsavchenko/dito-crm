# Програма лояльності (бонусна система) — варіанти реалізації

Документ для обговорення з клієнтом. Мета — вибрати механіку нарахування
та канал, через який клієнт отримує і використовує бонуси, з урахуванням
того, що мобільного застосунку й інтернет-магазину поки немає, але вони
планується.

---

## 1. Ключова ідея: розділяємо систему на два шари

Це головне рішення, від якого залежить вартість усього подальшого розвитку.

```
┌─────────────────────────────────────────────────────────┐
│  ЯДРО — бонусний рушій усередині Dito CRM               │
│  Правила, журнал транзакцій, баланси, рівні, звіти      │
│  Робиться ОДИН раз, однакове для всіх варіантів         │
└────────────────────────┬────────────────────────────────┘
                         │  публічний REST API
        ┌────────────────┼────────────────┬───────────────┐
        │                │                │               │
   ┌────▼────┐     ┌─────▼─────┐    ┌─────▼─────┐   ┌─────▼──────┐
   │  Каса   │     │ Telegram/ │    │  Wallet-  │   │  Майбутні: │
   │ (CRM)   │     │  Viber    │    │  картка   │   │  застосунок│
   │         │     │   бот     │    │  Apple/   │   │  та інтернет│
   │         │     │           │    │  Google   │   │  -магазин  │
   └─────────┘     └───────────┘    └───────────┘   └────────────┘
```

**Чому саме так.** Ядро — це 60–70 % усієї роботи, і воно не залежить від
того, через що клієнт бачить свій баланс. Канали підключаються до ядра
через один і той самий API. Тому:

- сьогодні запускаємо мінімальний канал і система вже працює;
- завтра додаємо бот або wallet-картку — ядро не переписуємо;
- коли з'явиться застосунок чи інтернет-магазин, вони підключаються
  **тим самим API**, що й каса. Жодної міграції даних, жодної переробки.

Це і є пряма відповідь на вимогу «легко інтегрувати в майбутній додаток».

## 2. Що входить у ядро (однаково в усіх варіантах)

| Компонент | Опис |
|---|---|
| Журнал транзакцій | Незмінний (append-only) реєстр усіх нарахувань і списань. Баланс = сума журналу. Повна історія по кожному клієнту, будь-яка операція доказова |
| Правила нарахування | Відсоток кешбеку, виключені категорії, поведінка зі знижковими позиціями |
| Правила списання | Максимальна частка чека, мінімальний поріг, заборона «бонуси на бонуси» |
| Рівні (за потреби) | Пороги за сумою покупок, різний % на кожному рівні |
| Карантин бонусів | Нараховані бали активуються через N днів — захист від зловживань із поверненнями |
| Згоряння | Термін дії з відліком по кожному нарахуванню окремо (FIFO) |
| Повернення товару | Автоматичне сторно нарахування + повернення списаних балів клієнту |
| Адмінка | Картки клієнтів, історія, ручне коригування з обов'язковим коментарем |
| Звіт «Зобов'язання» | Скільки бонусів роздано і не витрачено — це фінансовий борг бізнесу перед клієнтами |
| REST API | Єдина точка входу для каси, бота, картки, майбутнього магазину й застосунку |

Ядро вбудовується як окремий модуль CRM із фіча-флагом, тобто вмикається
пер-тенант — як і решта модулів платформи.

## 3. Вибір №1: механіка лояльності

Це те, що клієнт має обрати за бізнес-логікою. Технічно всі варіанти
підтримує одне ядро — різниця лише в конфігурації.

| Механіка | Як працює | Кому підходить | Складність |
|---|---|---|---|
| **Кешбек балами** | 3–5 % від чека повертається балами, 1 бал = 1 грн | Універсально. Найзрозуміліше клієнтам | Базова |
| **Рівні (Silver/Gold/Platinum)** | % зростає із сумою покупок за період | Середній і високий чек, повторні покупки | +невелика |
| **Штампи** | 6 покупок — сьома в подарунок | Кава, б'юті, послуги з частим візитом | +невелика |
| **Фіксована знижка на картку** | Не бали, а % знижки одразу | Ті, хто не хоче морочитись із балами | Базова |
| **Реферальна** | Бонус за приведеного друга | Розігрів бази на старті | Середня |
| **Персональні акції** | Бонус на день народження, «давно не заходили», подвійний кешбек на категорію | Утримання, реактивація | Середня |

**Рекомендація:** старт із кешбеку + день народження. Рівні додати
другим етапом, коли накопичиться статистика — тоді пороги ставляться за
реальними даними, а не навмання. Пороги, поставлені «на око», потім
дуже болісно змінювати: клієнти сприймають це як обман.

## 4. Вибір №2: канал — як клієнт бачить і використовує бонуси

Це і є основне питання за відсутності застосунку.

### Варіант A. Ідентифікація за номером телефону (базовий)

Клієнт називає номер на касі — касир бачить баланс, застосовує списання.
Баланс друкується в чеку, після покупки надсилається SMS.

- ✅ Найшвидший запуск, нуль зовнішніх залежностей, нуль абонплати
- ✅ Працює для будь-якого клієнта, включно з тими, хто без смартфона
- ❌ Між покупками клієнт не бачить баланс → залученість низька
- ❌ SMS платні (орієнтовно 0,7–1,5 грн за штуку — уточнити в провайдера)

**Це фундамент. Він потрібен у будь-якому разі** — навіть у преміум-пакеті
касир мусить уміти знайти клієнта за телефоном.

---

### Варіант B. Веб-кабінет клієнта (PWA)

Сторінка на кшталт `bonus.brand.com`: вхід за номером телефону з SMS-кодом,
баланс, історія, персональний QR-код для каси. Додається на домашній екран
як застосунок.

- ✅ Жодної залежності від Apple, Google чи месенджерів
- ✅ **Це вже перший крок до інтернет-магазину** — авторизація, кабінет,
  профіль клієнта роблять один раз і потім перевикористовують
- ✅ Працює на всіх пристроях, включно з десктопом
- ❌ Клієнта треба щоразу мотивувати зайти — сам не нагадає
- ❌ Push-повідомлення на iOS обмежені (працюють лише після додавання на
  екран «Додому»)

---

### Варіант C. Картка в Apple Wallet / Google Wallet

Саме те, на чому будує пропозицію Loyallyst. Клієнт сканує QR — картка
падає в стандартний гаманець телефону. Баланс на ній оновлюється сам.

- ✅ Картка завжди під рукою, поруч із банківськими — не губиться
- ✅ Баланс оновлюється автоматично, без відкриття будь-чого
- ✅ **Push-повідомлення безкоштовні** — заміна дорогим SMS
- ✅ Геолокаційне нагадування: картка спливає на екрані блокування біля
  магазину
- ✅ Нічого не треба встановлювати — головний аргумент для клієнтів
- ❌ Потрібен обліковий запис Apple Developer (~$99/рік) і робота з
  сертифікатами, або абонплата провайдеру (PassKit — орієнтовно від
  $39,5/міс за акаунт)
- ❌ Дизайн картки жорстко обмежений шаблонами Apple/Google
- ❌ Немає повноцінного «кабінету» — лише картка

---

### Варіант D. Telegram / Viber-бот

Для українського ринку — найсильніше співвідношення «ефект / вартість».

- ✅ Аудиторія вже в месенджері, встановлювати нічого не треба
- ✅ **Розсилки безкоштовні** — повністю замінюють SMS-бюджет
- ✅ Номер телефону отримується в один тап (кнопка «Поділитися контактом»)
  — реєстрація за 5 секунд, без введення й помилок
- ✅ Можна одразу дати більше, ніж картка: історія покупок, статус ремонту,
  запис на послугу, підтримка
- ✅ Розробка помітно дешевша за застосунок
- ❌ Залежність від платформи месенджера та її правил
- ❌ Частина аудиторії (переважно старша) месенджерами не користується

---

### Варіант E. Готове рішення (Loyallyst і аналоги) + інтеграція

Замість власної розробки — підключення зовнішнього сервісу.

- ✅ Запуск за тижні, канали вже готові
- ✅ Нуль витрат на розробку ядра
- ❌ **Абонплата помножується на кожного тенанта** — для white-label
  платформи це прямо з'їдає маржу
- ❌ База клієнтів і транзакції лежать у третьої сторони; при переході
  до власного рішення це болісна міграція
- ❌ Бонуси живуть окремо від CRM: продажі в одній системі, лояльність в
  іншій, наскрізної аналітики немає
- ❌ Обмежена кастомізація — механіку робимо ту, яку дозволяє вендор
- ❌ **Стратегічний ризик:** ви продаєте власну CRM, але ключова частина
  цінності належить чужому сервісу, який може змінити ціни або умови

**Коли це виправдано:** якщо потрібно перевірити гіпотезу за місяць і
бюджет на розробку відсутній. Як довгострокове рішення для платформи —
ні.

## 6. Комерційні пакети для клієнта

### Пакет «Старт»
**Ядро + каса + SMS** (варіант A)

Повноцінна бонусна система: нарахування, списання, повернення, звіти.
Клієнт ідентифікується за телефоном, баланс — у чеку та SMS.

*Для кого:* один магазин, хочуть швидко перевірити, чи взагалі працює.

---

### Пакет «Стандарт» — рекомендований
**Ядро + каса + Telegram-бот** (A + D)

Те саме плюс бот: клієнт сам бачить баланс, отримує безкоштовні
сповіщення про нарахування й акції, показує QR на касі.

*Чому рекомендуємо:* бот закриває 90 % цінності wallet-картки, коштує
дешевше, дає безкоштовну комунікацію замість SMS-бюджету і не залежить
від сертифікатів Apple. Для українського ринку — оптимум.

---

### Пакет «Преміум»
**Ядро + каса + бот + wallet-картка + веб-кабінет** (A + B + C + D)

Клієнт сам обирає зручний канал. Веб-кабінет одночасно є фундаментом
майбутнього інтернет-магазину — авторизація й особистий кабінет уже
будуть готові.

*Для кого:* мережа, кілька точок, є плани на магазин і застосунок.

---

## 7. Гарантія майбутньої інтеграції

Що конкретно закладаємо **зараз**, щоб застосунок та інтернет-магазин
підключилися без переробок:

1. **Публічний REST API з першого дня.** Каса в CRM працює через той самий
   API, що потім використає магазин. Якщо API годиться для власної каси —
   він точно годиться для стороннього клієнта.
2. **Ідемпотентність операцій.** Кожне нарахування має унікальний ключ
   операції. Мобільний застосунок у метро втратив зв'язок і повторив
   запит — дубля бонусів не буде.
3. **Вебхуки.** Магазин чи застосунок підписуються на події «бонуси
   нараховано», «рівень підвищено», «бали скоро згорять» — і надсилають
   власні сповіщення.
4. **Телефон як наскрізний ідентифікатор.** Один клієнт — один профіль,
   незалежно від того, купив він на касі, в застосунку чи в магазині.
   Бонуси спільні. Це те, що потім називають омніканальністю, і закласти
   це на старті нічого не коштує, а додати пізніше — дорого.
5. **Правила лояльності в конфігурації, а не в коді.** Змінити кешбек із
   3 % на 5 % — це налаштування в адмінці, а не реліз.

## 8. Рекомендація

**Пакет «Стандарт»** (ядро + каса + Telegram-бот), із закладеним API та
веб-кабінетом другим етапом.

Обґрунтування:

- ядро власне → дані наші, маржа не з'їдається абонплатою на кожного
  тенанта, механіка не обмежена чужим вендором;
- бот дає клієнтові те саме, що wallet-картка Loyallyst (баланс під рукою
  + безкоштовні пуші), але дешевше й швидше;
- wallet-картку додаємо третім етапом як допродаж — вона добре
  продається візуально й підвищує чек пакета;
- веб-кабінет паралельно стає фундаментом інтернет-магазину, тобто
  ці гроші клієнт витрачає двічі за одну ціну.

## 9. Питання, які треба уточнити в клієнта

Від відповідей залежить і механіка, і канал, і оцінка:

1. Скільки клієнтів у базі зараз і чи є в ній номери телефонів?
2. Скільки торгових точок і чи планується мережа?
3. Яка каса використовується зараз — потрібна інтеграція з наявним POS
   чи достатньо касового модуля Dito CRM?
4. Середній чек і частота повторних покупок — від цього залежить, що
   доречніше: кешбек, рівні чи штампи.
5. Який відсоток кешбеку економіка витримує? (це рішення власника, не
   технічне — фактично це знижка з маржі)
6. Чи потрібні бонуси за ремонт/послуги, чи лише за товари?
7. Коли орієнтовно планується інтернет-магазин або застосунок — від
   цього залежить, чи робити веб-кабінет одразу.
8. Чи є бюджет на SMS, чи принципово обійтися безкоштовними каналами?

## 10. Наступний крок

Після вибору пакета — деталізована технічна специфікація ядра
(модель даних, API-контракти, екрани адмінки) і календарний план з
розбивкою на етапи.
